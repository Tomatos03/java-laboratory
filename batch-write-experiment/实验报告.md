# 批量写入性能对比实验报告

## 实验概述

本实验对比了分段写入（Batch Write）和一次性写入（Single Write）两种数据库写入方式的性能差异，旨在为大数据量写入场景提供性能参考和最佳实践建议。

## 实验目标

1. 对比分段写入和一次性写入的性能差异
2. 评估不同批大小对性能的影响
3. 分析内存占用与性能的权衡
4. 为生产环境提供写入策略建议

## 实验环境

| 项目 | 配置 |
|------|------|
| 数据库 | MySQL 8.0 |
| ORM 框架 | MyBatis-Plus 3.5.6 |
| 应用框架 | Spring Boot 3.2.5 |
| Java 版本 | Java 17 |
| 表结构 | t_product（包含 id, name, price, quantity, created_at） |
| 网络 | 本地 Docker 容器 |


## 实验步骤

1. **启动 MySQL 服务**

   ```bash
   cd batch-write-experiment/docs/docker
   docker compose up -d
   ```

   等待 MySQL 完全启动（约 10-15 秒），确认容器运行状态：
   ```bash
   docker compose ps
   ```

2. **启动应用**

   ```bash
   mvn spring-boot:run -pl batch-write-experiment
   ```

   应用启动时会自动创建数据库表。看到以下日志表示启动成功：
   ```
   ✓ Database table t_product created successfully
   ```

3. **执行性能测试**

   依次执行以下测试命令，记录每个测试的结果：

   - 100,000 条记录 - 批量写入（批大小 1,000）
     ```bash
     curl -X POST "http://localhost:8080/api/batch/write?size=1000&count=100000"
     ```

   - 100,000 条记录 - 一次性写入
     ```bash
     curl -X POST "http://localhost:8080/api/single/write?count=100000"
     ```

   - 300,000 条记录 - 一次性写入
     ```bash
     curl -X POST "http://localhost:8080/api/single/write?count=300000"
     ```

   - 300,000 条记录 - 批量写入（批大小 1,000）
     ```bash
     curl -X POST "http://localhost:8080/api/batch/write?size=1000&count=300000"
     ```

   - 300,000 条记录 - 批量写入（批大小 3,000）
     ```bash
     curl -X POST "http://localhost:8080/api/batch/write?size=3000&count=300000"
     ```

   - 300,000 条记录 - 批量写入（批大小 4,000）
     ```bash
     curl -X POST "http://localhost:8080/api/batch/write?size=4000&count=300000"
     ```

4. **验证数据**

   查询数据库中的记录总数：
   ```bash
   curl -X GET "http://localhost:8080/api/product/count"
   ```

   查询特定产品：
   ```bash
   curl -X GET "http://localhost:8080/api/product/1"
   ```

5. **停止应用**

   在应用运行的终端中按 `Ctrl+C`

6. **停止 MySQL 容器**

   ```bash
   cd batch-write-experiment/docs/docker
   docker compose down
   ```

7. **清理数据（可选）**

   ```bash
   docker compose down -v  # 删除数据卷
   ```

## 实验数据

| 测试类型 | 批大小 | 总数 | 耗时(ms) | 吞吐量(records/sec) |
|---------|--------|------|---------|-------------------|

| 单次写入 | N/A | 100,000 | 18,581 | 5,422.99 |
| 单次写入 | N/A | 300,000 | 54,125 | 5,584.72 |
| 批量写入 | 1,000 | 300,000 | 52,482 | 5,762.80 |

| 批量写入 | 4,000 | 300,000 | 54,457 | 5,548.67 |

### 数据分析

#### 100,000 条记录对比

| 指标 | 批量写入(1K) | 单次写入 | 差异 |
|------|------------|--------|------|
| 耗时(ms) | 19,038 | 18,581 | +2.46% |
| 吞吐量(records/sec) | 5,303.07 | 5,422.99 | -2.21% |

**结论**：在 100,000 条记录的场景下，两种方式性能基本相当，单次写入略快 2.46%。

#### 300,000 条记录对比

**单次写入**：
- 耗时：54,125 ms
- 吞吐量：5,584.72 records/sec

**批量写入（不同批大小）**：

| 批大小 | 耗时(ms) | 吞吐量(records/sec) | vs 单次写入 |
|--------|---------|-------------------|-----------|
| 1,000 | 52,482 | 5,762.80 | -3.04% 耗时 |
| 3,000 | 51,943 | 5,820.16 | -4.06% 耗时 |
| 4,000 | 54,457 | 5,548.67 | +0.61% 耗时 |

**关键发现**：
- 批大小为 3,000 时性能最优，比单次写入快 4.06%
- 批大小为 1,000 时也有 3.04% 的性能优势
- 批大小为 4,000 时性能开始下降，接近单次写入水平

#### 吞吐量对比

```
吞吐量范围：5,303 - 5,820 records/sec
平均吞吐量：5,590 records/sec
最高吞吐量：5,820 records/sec（批大小 3,000）
最低吞吐量：5,303 records/sec（批大小 1,000，100K 数据）
```

## 实验结论

### 主要发现

1. **性能差异微小**：分段写入和一次性写入的性能差异在 ±5% 以内，基本可以认为性能相当。

2. **批大小的影响**：
   - 批大小 1,000-3,000 时性能较优
   - 批大小过大（4,000+）可能导致性能下降
   - 最优批大小约为 3,000 条/批

3. **数据量的影响**：
   - 吞吐量随数据量增加而略有提升（5,303 → 5,820 records/sec）
   - 这可能与数据库缓冲区预热有关

4. **分段写入的优势**：
   - **内存安全**：不会因为一次性加载大量数据而导致内存溢出
   - **可控性**：可以实时监控进度，支持中断和恢复
   - **事务灵活性**：可以针对每个批次进行错误处理

5. **一次性写入的优势**：
   - **事务一致性**：单个事务保证原子性
   - **代码简洁**：实现逻辑更直接
