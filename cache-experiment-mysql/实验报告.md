# MySQL 直查 vs Redis 缓存 性能对比实验

## 实验目的

对比 MySQL 数据库直查与 Redis 缓存两种方式在不同查询场景下的响应时间差异，验证引入缓存对读取性能的提升效果，并与 H2 内存数据库实验形成对照，观察真实数据库场景下缓存的收益变化。

## 实验环境

| 组件 | 版本/配置 |
|------|-----------|
| JDK | 17 |
| Spring Boot | 3.2.5 |
| MySQL | 8.0（Docker） |
| Redis | 6.x（Docker） |
| MyBatis-Plus | 3.5.6 |

### 数据规模

- `t_user` 表：50 条记录
- `t_order` 表：60 条记录（用户 1-20 各有 3 条订单）

## 环境准备

```bash
# 1. 启动 MySQL + Redis
cd cache-experiment-mysql/docs/docker
docker compose up -d

# 2. 编译项目
mvn clean compile -pl cache-experiment-mysql

# 3. 启动应用
mvn spring-boot:run -pl cache-experiment-mysql
```

## 实验步骤

使用 ab 压测对比两种模式：`/api/direct/**`（直查 DB）vs `/api/cache/**`（缓存命中）。

```bash
# 单表查询
ab -n 10000 -c 1000 http://localhost:8081/api/direct/users/1
ab -n 10000 -c 1000 http://localhost:8081/api/cache/users/1

# 连接查询
ab -n 10000 -c 1000 http://localhost:8081/api/direct/users/1/orders
ab -n 10000 -c 1000 http://localhost:8081/api/cache/users/1/orders
```

## 预期结果

| 对比项 | 预期结论 |
|--------|----------|
| 直查 vs 缓存未命中 | 缓存未命中略慢于直查（多了 Redis 写入开销） |
| 直查 vs 缓存命中 | 缓存命中显著快于直查（跳过 DB 查询和网络 I/O） |
| MySQL vs H2 | MySQL 直查耗时高于 H2（网络 I/O + 磁盘 I/O），缓存相对收益更大 |

## 实际测试数据

### 单表查询（SELECT * FROM t_user WHERE id = ?）

#### 压测数据（ab -n 10000 -c 1000）

| 指标 | 直查 DB | 缓存命中 | 提升幅度 |
|------|---------|---------|---------|
| QPS  | 6878.23 | 10614.82 | +54.3% |
| 平均耗时 (ms) | 145.39 | 94.21 | -35.2% |
| P99 耗时 (ms) | 1142 | 145 | -87.3% |

### 连接查询（SELECT u.*, o.* FROM t_user u JOIN t_order o ON u.id = o.user_id WHERE u.id = ?）

#### 压测数据（ab -n 10000 -c 1000）

| 指标 | 直查 DB | 缓存命中 | 提升幅度 |
|------|---------|---------|---------|
| QPS  | 5930.69 | 11060.61 | +86.5% |
| 平均耗时 (ms) | 168.61 | 90.41 | -46.4% |
| P99 耗时 (ms) | 262 | 145 | -44.7% |

> [!NOTE]
> **P99 耗时**：指 99% 的请求都在该时间内完成，仅 1% 的请求比它更慢。相比平均耗时，P99 更能反映尾部延迟（long tail），避免少数极端值被平均值掩盖。例如 P99=244ms 表示 99% 的请求在 244ms 内完成。

## 结论

### 测试结果汇总

| 场景 | 指标 | 直查 DB | 缓存命中 | 提升幅度 |
|------|------|---------|---------|---------|
| 单表查询 | QPS | 6878.23 | 10614.82 | +54.3% |
| 单表查询 | 平均耗时 | 145.39 ms | 94.21 ms | -35.2% |
| 单表查询 | P99 耗时 | 1142 ms | 145 ms | -87.3% |
| 连接查询 | QPS | 5930.69 | 11060.61 | +86.5% |
| 连接查询 | 平均耗时 | 168.61 ms | 90.41 ms | -46.4% |
| 连接查询 | P99 耗时 | 262 ms | 145 ms | -44.7% |

### 分析

**单表查询**：缓存命中相比直查 DB，QPS 提升 54.3%，平均耗时降低 35.2%。最显著的改善体现在 P99 尾部延迟上——从 1142ms 降至 145ms（降幅 87.3%），说明缓存有效消除了 DB 查询在高并发下的长尾抖动。直查 DB 的 P99 与中位数（80ms）差距极大，反映出 MySQL 在并发场景下存在明显的尾部延迟；而缓存命中后 P99（145ms）与中位数（88ms）差距较小，表现更加稳定。

**连接查询**：缓存命中相比直查 DB，QPS 提升 86.5%（高于单表的 54.3%），平均耗时降低 46.4%。连接查询的直查 DB 耗时（168.61ms）高于单表（145.39ms），但缓存命中后两者基本持平（90.41ms vs 94.21ms），说明 JOIN 的额外开销在缓存模式下被完全消除。P99 方面，连接查询直查 DB 的尾部抖动（262ms）反而小于单表（1142ms），推测是 JOIN 查询的锁竞争模式不同所致。

**总体结论**：缓存对连接查询的收益更大（+86.5% vs +54.3% QPS），因为 JOIN 查询的 DB 开销更高，缓存跳过这部分后收益更明显。而缓存命中后两种查询的性能趋于一致，说明瓶颈已从 DB 转移到 Redis 网络 I/O。

### 与 H2 实验对比

| 对比维度 | H2 实验 | MySQL 实验 | 差异原因 |
|----------|---------|------------|----------|
| 单表直查延迟 | 极低（内存库） | 145.39ms（均值） | MySQL 需要网络 I/O + 磁盘 I/O |
| 单表缓存收益 | 中等（+25% QPS） | +54.3% QPS | DB 查询越慢，缓存收益越大 |
| 连接直查延迟 | 极低 | 168.61ms（均值） | MySQL JOIN 涉及磁盘读取和网络传输 |
| 连接缓存收益 | - | +86.5% QPS | JOIN 开销越高，缓存跳过后收益越大 |
| P99 改善 | - | 单表 -87.3%，连接 -44.7% | MySQL 并发下尾部抖动远大于 H2，缓存平滑效果更显著 |
