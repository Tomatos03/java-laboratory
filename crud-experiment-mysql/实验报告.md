# MySQL 有索引 vs 无索引 单次 SQL 执行时间对比实验

## 实验目的

在大表（100 万条记录）场景下，对比 MySQL 有索引与无索引两种表结构在查询、更新和删除操作上的执行时间差异，验证索引对 `WHERE` 条件查询、`UPDATE` 和 `DELETE` 操作的实际加速效果。

## 实验环境

| 组件 | 版本/配置 |
|------|-----------|
| JDK | 17 |
| Spring Boot | 3.2.5 |
| MySQL | 8.0（Docker） |
| MyBatis-Plus | 3.5.6 |

### 数据规模

| 表名 | 记录数 | 索引情况 |
|------|--------|----------|
| `t_user_no_index` | 1,000,000 | 仅主键 `id` |
| `t_user_with_index` | 1,000,000 | 主键 `id` + `idx_user_id` + `idx_status` |

两张表的字段结构完全一致：

```sql
id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id INT NOT NULL,
username VARCHAR(100) NOT NULL,
email VARCHAR(100) NOT NULL,
phone VARCHAR(20),
address VARCHAR(255),
status INT DEFAULT 1,
create_time TIMESTAMP,
update_time TIMESTAMP
```

有索引表额外创建了：
```sql
INDEX idx_user_id (user_id)
INDEX idx_status (status)
```

## 实验步骤

通过调用 API 接口，观察 `@TimingTrack` 记录的单次 SQL 执行时间。

### 查询操作

```bash
# 无索引查询
curl http://localhost:8082/api/no-index/users/query/{user_id}

# 有索引查询
curl http://localhost:8082/api/with-index/users/query/{user_id}
```

### 更新操作

```bash
# 无索引更新
curl -X PUT "http://localhost:8082/api/no-index/users/update/{user_id}?status=1"

# 有索引更新
curl -X PUT "http://localhost:8082/api/with-index/users/update/{user_id}?status=1"
```

### 列表查询操作

```bash
# 无索引列表查询
curl http://localhost:8082/api/no-index/users/list/{user_id}

# 有索引列表查询
curl http://localhost:8082/api/with-index/users/list/{user_id}
```

### 删除操作

```bash
# 无索引删除
curl -X DELETE http://localhost:8082/api/no-index/users/delete/{user_id}

# 有索引删除
curl -X DELETE http://localhost:8082/api/with-index/users/delete/{user_id}
```

## 实际测试数据

### 单条查询

| 指标 | 无索引 | 有索引 | 提升幅度 |
|------|--------|--------|----------|
| 执行时间 (ms) | 415 | 1 | -99.8% |

### 列表查询

| 指标 | 无索引 | 有索引 | 提升幅度 |
|------|--------|--------|----------|
| 执行时间 (ms) | 772 | 2 | -99.7% |

> [!NOTE]
> 列表查询返回同一 `user_id` 对应的所有记录（约 1000 条），无索引需全表扫描后筛选，有索引通过 B+ 树定位后顺序读取。测试时该 user_id 已被删除，返回 0 条，但全表扫描/索引定位的耗时差异仍有参考价值。

### 更新操作

| 指标 | 无索引 | 有索引 | 提升幅度 |
|------|--------|--------|----------|
| 执行时间 (ms) | 774 | 3 | -99.6% |

> [!NOTE]
> 无索引更新需要全表扫描定位目标行（100 万行），而有索引更新通过 B+ 树直接定位，耗时从 774ms 降至 3ms。

### 删除操作

| 指标 | 无索引 | 有索引 | 提升幅度 |
|------|--------|--------|----------|
| 执行时间 (ms) | 2137 | 980 | -54.1% |
| 删除行数 | 2001 | 2001 | - |

> [!NOTE]
> 删除操作需要先定位目标行再执行删除。无索引时定位等同全表扫描，有索引时通过 B+ 树快速定位。删除后还需维护索引结构。本次测试删除了 2001 条记录，索引加速效果（2.2 倍）明显弱于查询场景（415 倍），因为大量行的删除本身耗时占主导。

## 结论

### 测试结果汇总

| 场景 | 无索引 | 有索引 | 提升幅度 |
|------|--------|--------|----------|
| 单条查询 | 415 ms | 1 ms | -99.8% |
| 列表查询 | 772 ms | 2 ms | -99.7% |
| 更新 | 774 ms | 3 ms | -99.6% |
| 删除 | 2137 ms | 980 ms | -54.1% |

### 分析

**单条查询操作**：无索引查询耗时 415ms，有索引查询仅 1ms，性能差距达 415 倍。无索引时 `WHERE user_id = ?` 需要全表扫描 100 万行逐行比对，而有索引时通过 B+ 树直接定位，耗时可忽略不计。

**列表查询操作**：无索引耗时 772ms，有索引仅 2ms，性能差距达 386 倍。与单条查询（415 倍）量级一致，说明索引对定位操作的加速效果稳定，返回行数多少对定位耗时影响较小。

**更新操作**：无索引更新耗时 774ms，有索引更新仅 3ms，性能差距达 258 倍。`UPDATE ... WHERE user_id = ?` 需要先定位目标行再执行更新，无索引时定位步骤等同全表扫描，而有索引时快速定位后仅需更新少量索引页。

**删除操作**：无索引删除耗时 2137ms，有索引删除 980ms，性能差距约 2.2 倍。删除 2001 条记录本身耗时占主导（需逐行删除并维护索引），索引的定位优势被大量行删除的开销稀释。相比更新操作（258 倍差距），批量删除场景下索引的加速效果明显减弱。

**总体结论**：在 100 万条记录的大表场景下，索引对查询和更新操作有质的提升（加速 200-400 倍），对删除操作也有明显加速（2.2 倍）但幅度较小。写操作（更新、删除）的无索引耗时高于读操作（查询），因为写操作除了全表扫描定位外还需写回数据页和维护索引。批量删除场景下，索引的定位优势被大量行删除的开销稀释。

### 索引原理说明

**无索引查询**：MySQL 对 `WHERE user_id = ?` 需要执行全表扫描（Full Table Scan），逐行比对 `user_id` 值。在 100 万条记录下，意味着每次查询最多扫描 100 万行。

**有索引查询**：`idx_user_id` 索引基于 B+ 树结构，查询时通过索引树定位，时间复杂度为 O(log n)。100 万条记录的 B+ 树深度通常为 3-4 层，仅需数次磁盘 I/O 即可定位目标行。

**更新操作的索引影响**：`UPDATE ... WHERE user_id = ?` 需要先定位目标行再执行更新。无索引时定位步骤等同全表扫描；有索引时可快速定位，但更新后还需维护索引结构，因此提升幅度通常小于查询场景。

**删除操作的索引影响**：`DELETE ... WHERE user_id = ?` 需要先定位目标行再执行删除。无索引时定位步骤等同全表扫描；有索引时可快速定位，但批量删除大量行时，逐行删除和索引维护的开销占主导，索引的定位优势被稀释，提升幅度明显弱于查询和更新场景。
